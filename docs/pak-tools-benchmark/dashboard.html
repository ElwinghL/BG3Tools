Méthodologie et limitations

Chaque outil est mesuré dans son jus (perf native/brute, sans pont intermédiaire) ET, quand c'est pertinent, dans le pipeline réel de BG3Tools (binding FFI, subprocess Wine/Proton) — deux séries distinctes plutôt qu'un chiffre mélangé.

Toute la lecture est mesurée sur de vrais .pak du jeu (pas de fixtures synthétiques) : 48 fichiers du jeu de base, 205 de mods actifs. Les 22 erreurs de bg3pythonpaklib/bg3rustpaklib sur le lot « jeu de base » sont attendues : ce sont des parties de continuation d'archives multi-parties (*_N.pak, ex. Textures_1.pak) — seule la partie 0 porte l'en-tête LSPK ; le taux d'erreur réel sur ces 48 fichiers est 0/48.

Divine.exe sous Linux passe par Wine/Proton pour la lecture — non représentatif du natif Windows (gap déjà documenté dans les README de bg3pythonpaklib/bg3rustpaklib). Run complet (mode per-file, un lancement Wine par .pak) sur les 48 fichiers du jeu de base : 42 réussis, 6 en échec (3 timeouts sur de gros fichiers, 3 crashs probablement OOM sur des archives volumineuses/multi-parties — Gustav.pak, Textures.pak, VirtualTextures.pak). Les 205 .pak de mods n'ont pas été passés par Divine.exe (mode per-file trop lent à cette échelle, mode batch natif cassé en amont — bug LSLib dans CommandLineArguments.GetResourceFormatByString, voir l'encart ci-dessous).

Création/édition non exercée pour Divine.exe cette passe (pas de binaire Wine disponible dans cet environnement) ; le code d'invocation existe et suit le pattern déjà en prod, mais reste non testé en exécution.
